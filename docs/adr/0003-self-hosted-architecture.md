# ADR 0003：首版技术架构与自托管交付

- 日期：2026-11-04
- 状态：采用；首版应用与 Docker 交付已实现，验证证据持续记录在 [验收记录](../verification/v1-validation.md)，目标生产部署尚未执行。
- 关联：[ADR 0001](0001-project-baseline.md)、[ADR 0002](0002-ai-information-v1.md)、[首版产品设计](../design/v1-product-design.md)、[来源策略](../design/v1-source-strategy.md)。
- 替代范围：将此前“应用框架、数据库、身份与部署方案待定”具体化；产品范围、私有性、Ant Design 和上线门禁继续有效。

## 背景与已确认条件

用户已通过首版产品设计，允许开发可运行版本，计划在自己的服务器安装 Docker，并要求 README 包含完整项目介绍和安装流程；新建 Git 仓库已获授权。仓库创建、上传和实际部署结果须由对应操作证据确认，不能从本 ADR 推断已完成。

服务器操作系统、CPU 架构、资源、域名和网络条件尚未提供。本次以 **Linux + Docker Engine + Docker Compose** 为交付目标，这是待实际环境核验的假设；不假定用户已有云数据库、身份服务或付费模型账号。视觉采用用户确认的第二版布局和第一版浅色侧栏，选定稿保存在 [设计图](../../design/selected-desktop.png)。

## 决策

采用单仓库的模块化单体：**Next.js + TypeScript + Ant Design + PostgreSQL + Better Auth + 独立 worker + pg-boss**，通过 **Caddy + Docker Compose** 自托管。

| 部分 | 职责与边界 |
| --- | --- |
| Next.js / TypeScript | 响应式页面、服务端接口和共享业务模块；私有数据必须在服务端授权后访问 |
| Ant Design | 唯一基础 UI 体系，使用项目 token；按官方 Next.js 集成处理首屏样式，双端能力一致 |
| PostgreSQL | 业务数据、个人整理状态、身份会话、采集执行记录及任务队列的持久存储 |
| Better Auth | 密码认证、服务端会话、TOTP 与恢复码；项目另外强制唯一拥有者和 MFA 门禁 |
| worker / pg-boss | 独立常驻进程执行计划任务、来源采集、重试和可选摘要，不依赖浏览器打开页面 |
| Caddy | 单一对外入口、TLS 和反向代理；应用与数据库端口不直接暴露公网 |
| Docker Compose | 单机服务编排、健康检查、持久卷及可重复部署；不引入 Kubernetes 或额外 Redis |

web 与 worker 使用同一代码库和业务规则，按各自运行入口构建产物；独立进程是为了隔离请求处理与后台任务，不形成需要分别维护的微服务。身份、业务和任务模块使用明确的表/命名空间与版本化迁移，运行角色只持有所需权限。

Next.js 官方支持自托管并建议使用反向代理；Ant Design 有对应集成方案。具体依赖版本、受支持 Node.js LTS、PostgreSQL 主版本和镜像摘要在实现时锁定，不使用未验证的预发布版本或浮动 `latest` 作为生产依据。[Next.js 自托管](https://nextjs.org/docs/app/guides/self-hosting)、[Ant Design 集成](https://ant.design/docs/react/use-with-next/)

## 备选方案与取舍

| 方案 | 适用优势 | 本次未采用的原因 |
| --- | --- | --- |
| React/Vite + FastAPI + SQLite | 静态前端、无需独立数据库服务，适合单机低负载和资源很紧的环境 | 同时维护 TypeScript/Python；可靠任务调度与 MFA 需另行集成；后台采集与交互写入还需处理 SQLite 写锁和备份边界 |
| Next.js + PostgreSQL（采用） | 共享 TypeScript 业务模块；成熟认证插件；用同一数据库承担持久任务队列 | 增加数据库常驻服务、连接管理和数据库升级工作；Next.js 的私有内容缓存需显式审查 |
| 托管数据库或身份平台 | 可转移部分运维工作 | 用户目标是自己的服务器；目前没有必要将核心可用性、账号或费用依赖绑定到新云服务 |

选择 PostgreSQL 的主要理由是可靠调度、并发事务与维护方式一致，不宣称首版信息量已超过 SQLite 能力。SQLite 官方认可其低至中等流量网站用途；WAL 要求同机且不适合网络文件系统，在线备份也有专门 API。若真实服务器资源不足，可通过新的 ADR 调整，不能悄悄切库或降低验收标准。[SQLite 使用边界](https://www.sqlite.org/whentouse.html)、[WAL](https://www.sqlite.org/wal.html)、[在线备份](https://www.sqlite.org/backup.html)

## 定时采集与一致性

- 模型/公告来源每 60 分钟检查；GitHub 发现、快照和 Release 每 6 小时检查。实际节奏、首次回看范围、限流退避和增长窗口遵循来源策略。
- 计划、任务状态、执行结果和最近成功时间持久化。worker 在没有浏览器连接时仍运行；健康检查同时关注进程存活、心跳和任务延迟。
- 使用来源级互斥、有界并发、稳定事件唯一键和事务避免重复入站；重试仍须业务幂等，不能把队列可靠性等同于外部副作用绝不重复。
- 进程或服务器中断后恢复任务，合并同源过期检查并按来源可用历史补采；不密集重放全部错过的轮次，不伪造 GitHub 历史快照。
- 网页请求仅查询状态或提交任务，不承担定时器。AI 摘要为可选任务，失败不阻断规则分类和合格条目入站；人工修正与个人状态不被重采覆盖。
- worker 获取外部内容必须通过 [安全基线](../../SECURITY.md) 的 SSRF、超时、大小、重定向与输出处理要求；服务端凭据不进入任务日志或前端。

pg-boss 提供 PostgreSQL 持久队列、cron 调度、重试和并发策略，可避免额外维护消息代理；具体行为仍须通过断电、超时和重启测试验证。[pg-boss 官方文档](https://pgboss.io/)

## 唯一拥有者、MFA 与恢复

- 使用服务器管理命令初始化唯一拥有者；密码通过安全输入提供，不写入仓库、构建参数或日志。初始化必须可检测既有账号，不能每次启动重置密码，也不保留公开注册/初始化入口。
- 关闭公众注册及未采用的登录方式。业务服务每次验证真实服务端会话、固定拥有者身份和必要的认证状态；仅检查 Cookie 存在或隐藏页面不是授权。
- 默认采用密码 + TOTP，验证首次绑定代码后才允许访问业务。首次登录未绑定 MFA 时只开放受限配置流程；不允许直接调用 API 绕过该限制。
- 提供离线保存的一次性恢复码；默认不依赖短信或邮件服务。启用可信设备、其他身份提供商或邮件找回前另行定义安全边界，不隐式降低 MFA 要求。
- 会话 Cookie 使用 `HttpOnly`、`Secure` 和适当 `SameSite`；同源部署、明确受信来源、CSRF 防护及登录/二次验证限速均需配置与验证。私有响应不得进入共享页面缓存。
- 改密、账号恢复和凭据泄漏后撤销旧会话。恢复码遗失时仅允许通过服务器受限管理流程重置身份安全设置，记录脱敏审计并重新绑定 MFA；不能设置公开后门。
- 加密身份数据所依赖的应用密钥必须纳入独立安全保管；只有数据库副本而没有必要密钥，不视为可恢复备份。

Better Auth 提供关闭注册、服务端会话和 TOTP/恢复码能力；唯一拥有者、受限初始化与部署恢复流程属于本项目必须实现和测试的约束。[密码与注册选项](https://better-auth.com/docs/authentication/email-password)、[Next.js 会话集成](https://better-auth.com/docs/integrations/next)、[TOTP 与恢复码](https://better-auth.com/docs/plugins/2fa)

## 部署、迁移与版本维护

1. 在构建环境完成依赖检查、测试、构建和镜像生成；产物关联 Git 完整提交与镜像摘要。优先让服务器拉取已验证产物，避免把生产服务器当开发环境。
2. Compose 等 PostgreSQL 健康后执行一次迁移任务；迁移成功才启动依赖它的 web/worker。不能由多个进程各自抢跑迁移；数据库不可用时应用拒绝假就绪。
3. 生产只由 Caddy 对外提供服务。真实域名、DNS、80/443 可达性和证书持久目录需检查；仅有服务器 IP 或内部名称时不能声称公共证书已生效。
4. 升级前确认备份、暂停或排空不兼容的后台任务，再执行已在预发布验证的迁移与发布。优先使用向后兼容的新增—迁移—清理变更。
5. 应用可回滚至上一验证产物的前提是数据库兼容；不兼容时按数据恢复方案处理。首次发布验证撤下入口与保护现有数据的路径，不能假定存在上一生产版本。
6. PostgreSQL 主版本升级、认证库结构升级和队列结构升级分别在隔离环境演练；禁止仅替换容器标签而跳过数据迁移。依赖按计划检查、修复与小步升级。

Compose 的“容器已运行”不表示服务已就绪；应明确健康依赖与迁移完成条件。Caddy 自动 HTTPS 也有实际环境前提。[Compose 生产用法](https://docs.docker.com/compose/how-tos/production/)、[启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)、[Caddy HTTPS](https://caddyserver.com/docs/automatic-https)

## 数据备份与故障恢复

- 按 [上线门禁](../production-readiness.md) 至少每日生成一致性数据库备份，并在破坏性迁移前追加备份；默认用 `pg_dump` 生成可验证的备份产物，不直接复制运行中的数据库数据目录。
- 备份数据库、恢复所需配置说明及今后实际存在的附件；加密后复制到独立故障域。备份密钥与副本分开保管，应用运行凭据和备份权限分离。
- 沿用初定保留策略：每日 7 份、每周 4 份；RPO ≤ 24 小时、RTO ≤ 4 小时均是待演练验证的目标，不是当前服务保证。
- 恢复时先关闭入口并停止 worker 写入，恢复到隔离环境，验证记录和个人修正、身份恢复、来源状态与幂等行为，再按演练步骤切换。恢复后的旧运行任务不能造成重复入站。
- 备份成功、恢复成功、业务可用分别记录。首次上线前和季度恢复演练必须包括数据库实际恢复及关键业务路径，不能只验证备份文件存在。

`pg_dump` 提供事务一致的数据库快照并可在正常读写期间执行；权限、格式、目标版本与恢复命令在部署手册中明确。[PostgreSQL 备份文档](https://www.postgresql.org/docs/current/backup-dump.html)

## 资源、费用与交付要求

以 **2 vCPU、4 GiB 内存、至少 20 GiB 可用持久磁盘** 作为首轮部署验证的建议环境；这是项目测试起点，不是厂商最低要求或已测容量结论。实际需求取决于采集并发、快照保留、数据库索引、导出和备份；必须记录稳定运行及导入/备份时的峰值资源。若在服务器现场构建镜像，还要单独验证构建峰值。

常规费用来自服务器、域名、异地备份空间和网络；可选 AI API 另设预算并默认关闭。核心采集、规则整理和阅读不要求购买模型服务，不强制使用托管数据库。Git 托管套餐及分支保护能力仍按既定 Git 流程核实，不在本 ADR 中承诺具体价格。代码仓库按用户后续要求公开，见 [ADR 0004](0004-public-source-repository.md)。

README 必须包含项目用途、首版能力与限制、技术结构、所需服务器条件、Docker/Compose 安装前提、获取版本、配置项说明、首次启动/拥有者与 MFA 配置、来源设置、健康验证、升级、备份恢复和排障入口。提供不含真实秘密的配置样例；新用户应能按文档完成一次隔离部署，不能依赖聊天记录里的隐含步骤。

## 验收与当前差距

当前未取得服务器参数、域名、备份目的地和告警渠道，未执行生产部署。应用本地和 CI 的具体结果见 [验收记录](../verification/v1-validation.md)。技术决定不代表生产来源已启用、镜像已发布、远程保护已配置或服务可用。

- [ ] 确认 Linux 发行版、CPU 架构、资源、Docker/Compose、域名与网络，锁定兼容依赖和镜像。
- [ ] 按最终视觉方案完成桌面/手机页面及真实持久化闭环，通过适用类型、静态分析、测试与构建。
- [ ] 验证单用户授权、公众注册关闭、MFA 绑定/恢复、旧会话撤销、CSRF 和私有缓存隔离。
- [ ] 验证真实计划采集、手动重试、服务端限流、worker 重启、重复任务和人工修正保护。
- [ ] 验证 SSRF 门禁、秘密管理、日志脱敏、迁移、应用回滚及数据库恢复。
- [ ] 在目标架构执行 Compose 首次部署、升级与恢复演练，测量资源、性能和 RPO/RTO。
- [ ] 核验 README 的独立安装流程、远程仓库与分支保护、构建产物下载地址及发布证据。

上述清单作为部署验收要求，具体完成情况以验证证据为准，不将本地通过自动迁移为目标环境通过。后续变更数据库、身份边界、部署模式或引入长期付费依赖时，新增 ADR 说明原因、迁移方案和验收影响。
