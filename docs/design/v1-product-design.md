# 第一版产品设计：个人 AI 资讯中心

日期：2026-11-04。状态：产品设计稿，尚未实现。工作名称：Hulinger AI 资讯中心。

## 1. 已确认方向与设计默认

用户已明确：本轮只做设计，不写应用代码；首版收集整理网络 AI 信息，重点是模型更新和 GitHub 上有趣、热门的项目；内容自动收集并汇总到站内，允许人工修正；电脑和手机都要适配。沿用单人私有、Ant Design 和正式上线标准。

本文的页面划分、同步周期、首批来源规模和排序规则为可调整的首版设计默认，不代表用户逐项确认，也不代表已接入任何外部服务。技术栈、数据库、部署和付费模型服务保持待定。

一句话定位：打开自己的站点，快速了解关注的 AI 模型和开源项目发生了什么，把值得继续看的内容整理成可检索的个人资料。

## 2. 使用场景与首版结果

| 场景 | 用户得到什么 |
| --- | --- |
| 电脑上集中浏览 | 看最近动态，按模型、项目或主题筛选，快速阅读来源并批量整理 |
| 手机上碎片阅读 | 查看更新要点、打开原文、收藏或加入稍后读；返回后保留浏览位置 |
| 持续关注模型 | 在一个模型/产品的时间线查看不同版本、能力变化、预览转正式及停用信息 |
| 发现开源工具 | 看清项目解决什么问题、适用场景、原仓库和关注度信号，再决定是否跟踪 |
| 回找过去信息 | 按名称、关键词、标签、时间、来源和个人备注找回收藏或归档 |
| 收集结果有误 | 修改分类、标题或摘要，纠正重复合并；下次自动同步保留人工修正 |

首版体验目标：每天用约 5–10 分钟完成浏览和筛选；重要信息在 3 次主要操作内加入个人整理；手机可以独立完成查看、搜索、收藏、修改和来源管理。以上为后续可用性测试目标，尚无测量结果。

## 3. 内容范围

| 内容类型 | 首版纳入 | 主要信息 |
| --- | --- | --- |
| 模型与产品更新 | 新模型、版本/能力更新、预览/正式状态、API 可用性、官方价格变化、弃用或停用 | 厂商、模型/产品、版本或标识、事件类型、变化、适用范围、原始依据 |
| AI 开源项目 | 所选 AI 主题内的项目发现、关注项目的 Release、可解释的关注增长；默认正式版本，显式选择后包含预发布 | 仓库、用途、主题、语言、许可证状态、版本、Star 信号及观测时间 |
| 工具与生态动态 | 已选官方来源中的 AI 工具、SDK、开发平台的重要变化 | 产品、变化、与模型/项目的关系、来源 |

不承诺覆盖全网。首版不自动采集社交平台帖子、付费内容或登录后内容；论文全文、融资传闻、论坛评论、榜单评测、AI 聊天、邮件推送及公开社区暂不纳入。将来扩展必须先定义来源与验收。

同一内容只保存一份，通过分类、实体和标签出现在不同视图，不为首页、模型页和项目页各复制一份。

## 4. 首版功能优先级

| 优先级 | 能力 | 交付边界 |
| --- | --- | --- |
| 必需 | 拥有者登录与私有访问 | 页面、接口、搜索与导出均在服务端保护 |
| 必需 | 来源管理和自动同步 | 预设来源可启停，查看状态，手动重试；按规则定时采集，记录结果 |
| 必需 | 自动整理与入站 | 去重、规则分类、提取来源摘要、关联实体；合格条目直接进入信息流 |
| 必需 | AI 动态信息流 | 最近动态、未读、类型/主题/来源/时间筛选，显示来源和数据时效 |
| 必需 | 模型与项目视图 | 实体聚合、更新历史、关注/取消关注；项目热度解释可见 |
| 必需 | 搜索与个人整理 | 收藏、稍后读、标签、备注、归档、回收站、恢复、人工修正 |
| 必需 | 补充链接与数据导出 | 手动补充未覆盖资讯；导出结构化信息、来源、关联关系及个人整理状态 |
| 必需 | 双端适配 | 同一网站响应式布局，同账号已读、收藏、备注等状态跨设备同步 |
| 可选增强 | AI 中文摘要/翻译 | 默认不开启，需先明确模型服务、发送字段和费用；失败回退来源摘要 |
| 后续 | 原生 App、离线 PWA、系统分享扩展、订阅通知、多用户、公众分享 | 首版不依赖这些功能 |

“自动整理”首先指结构化、去重、分类和汇总；无需依赖付费大模型才能完成基本工作。没有来源摘要时显示标题及可核验元信息，明确“暂无摘要”，不能生成空洞文案冒充事实。

## 5. 信息从哪里来、怎样进入网站

主流程：**预设来源 → 定时获取 → 校验与标准化 → 去重/关联 → 分类及来源摘要 → 自动入站 → 阅读、关注和人工整理**。

异常分流：来源访问失败进入来源状态；内容疑似重复、缺少必要来源或事件归属冲突时，进入“需核对”，不阻塞其他有效条目。人工不需要逐条批准正常资讯。“需核对”在我的整理中可见，原内容和判断原因可查看。

- 优先官方 RSS/Atom 和 GitHub 官方 API；网页适配逐源验证后启用，不能将任意 URL 输入框做成无限制服务器抓取入口。
- 起步建议不超过 10 个公告来源、100 个持续观测的仓库，以便检查信息噪声和维护成本；达到上限时提示选择，不能静默漏采已关注对象。
- 模型/产品公告默认每 60 分钟检查；GitHub 项目发现及关注度快照默认每 6 小时检查。关注仓库 Release 随 GitHub 同步批次获取。周期可按来源规则和配额调整。
- 用户点击“刷新列表”只读取本站最新结果；“立即同步”单独触发受限的采集任务，同一来源重复点击合并，展示队列/运行状态。
- 首次启用公告源默认尝试补入最近 7 天；源只提供部分历史时明确显示覆盖情况。每源单次最多处理 100 条，再分页/分批继续，记录待处理量；不伪称单批已覆盖全部。
- 首次发现仓库创建项目资料和观测基线，不能把旧 Release 当作刚发布。后续正式更新按真实发布时间进入动态；历史内容标记“历史补入”。
- 暂停来源只停止后续采集，保留历史、收藏和备注；恢复时补抓可获得的区间，并明确无法追回的缺口。
- 已启用且完成首次同步的来源，距离最后成功检查超过两个当前计划周期时标记“同步延迟”；项目观测采用同样的两个快照周期规则。首次同步、手动暂停分别显示，不误报故障。资讯发布时间较早本身不构成“陈旧数据”。

候选来源、API 限制和来源分级见 [来源策略](v1-source-strategy.md)。上述同步周期是产品默认，不构成当前服务时效承诺。

## 6. 可信度、时间与摘要

每条资讯都能回答：**发生了什么、对象是谁、依据是什么、什么时候发生、本站多久前检查过**。

- 显示“官方公告”“项目维护者发布”“人工补充”等来源性质；厂商对性能的宣称注明为厂商描述，不自动视为独立测试结果。
- 原始发布时间、来源修改时间、首次发现时间、最后成功同步时间分别保存。来源只有日期时保持日期精度；缺少发布时间显示“发布时间未知，发现于…”。
- “最近动态”默认按可用的来源发布时间排列；缺失时使用首次发现时间并标明。历史补入保持原发布时间，不因今天抓到而伪装今天发生。
- 每条卡片显示主来源和原文入口，多来源详情可展开；来源互相矛盾时展示分歧并标记“需核对”。
- 摘要标明“来源摘要”“人工整理”或“AI 摘要”。用户的私人备注单独显示，不能混进原文摘录。
- 保留原始语言标题；若将来启用中文翻译，显示翻译性质并保留查看原题入口。摘要、翻译失败不能删除已入站资料。
- 无外部全文保存授权时，只保存所需元数据、有限来源摘要与链接；不把第三方全文批量镜像到本站。

## 7. GitHub 项目“热门”如何定义

默认页面名为“开源项目”，提供“近期发现”“累计 Star”“关注增长”“我关注的”几个明确视图；“有趣”通过项目用途、主题和个人推荐理由表达，不给一个不透明的 AI 分数。

| 信号 | 展示约定 |
| --- | --- |
| 累计 Star | 当前观测值及时间；不是当日新增或质量认证 |
| 近期发现 | 本站首次发现时间，与仓库创建时间分开；老项目也可能刚被发现 |
| 关注增长 | 同一仓库两次真实快照的 Star 净差；展示实际起止窗口和“本站观测” |
| GitHub Trending | 只有可追溯原榜证据才能标记，保留榜单范围、日期和原链接；首版自动采集不以它为依赖 |

增长支持接近 24 小时、7 天的观察窗口：取最新成功快照为终点，选择不晚于“终点减目标窗口”、且最接近该时刻的起点；起点偏离目标超过 6 小时则不进入该窗口排行。展示实际起止时间和跨度，不把更长区间标为精确 24 小时增长。只有缺少合格端点时显示“观测积累中/数据不足”；中间某次采集失败不使有效端点失效。终点已延迟时保留旧值并标记延迟，不参与当前增长排行。负差如实显示为净减少。新项目不因没有基线被藏掉，可在近期发现中查看。

只对已纳入观测的候选集合排序，显示采样范围与更新时间；搜索没有覆盖的项目不能被称为“不热门”。GitHub 暂时不可用时保留上次数据，标记“更新延迟”，不显示假 0。

## 8. 去重与人工修正

1. 同源优先以稳定条目 ID、仓库/Release ID 或规范来源 URL 去重；重复运行不得新增重复资讯。
2. 跨源仅在实体、版本/事件类型和关键事实足以确认一致时自动关联；只因标题相似或同属一个模型，不得强行合并。
3. 同一公告多家转述可以形成一个事件和多个来源；新版本、预览转正式、价格变化、停用属于独立事件。持续更新的日志按具体日期/条目处理，不能把整个更新日志视为单一事件。
4. 自动生成字段与人工覆盖值分开保存。人工修正标题、分类、摘要、标签或实体关联后，下一次采集只更新来源层；可查看差异并选择恢复自动值。
5. 支持将误合并条目拆开、手动合并相同事件，并保留关联依据。合并前预览个人标签、备注、已读及人工覆盖的冲突，不丢弃任何备注或覆盖；保留原事件关系以便撤销。拆分时选择个人整理的归属，记录禁止再次自动合并的关系，除非本人撤销。
6. 处理“需核对”可选择归类入站、关联已有事件或排除；同一分区的“已排除”筛选提供恢复入口。
7. 普通归档只改变个人视图；删除进入 30 天回收站。删除/排除后的条目保留最少的来源标识作为去重记录，避免下次同步原样复活；明确恢复后才重新显示。

永久删除清除该条目的内容、备注、人工覆盖，以及不再被其他事件引用的来源/修订内容。最少来源标识只保证同一来源条目不再次出现，其他来源的新报道仍可能成为候选；若同时完全清除去重标识，须说明同源内容也可能再次收集。来源更正或撤回保留可见提示，不能静默改写用户曾看到的关键事实。

## 9. 页面与导航

| 页面/视图 | 核心任务 |
| --- | --- |
| 最新动态（默认首页） | 查看最近收集的 AI 动态；按未读/关注、类型、主题、来源、时间筛选 |
| 模型更新 | 按厂商/模型浏览变化，进入模型时间线；关注感兴趣的对象 |
| 开源项目 | 发现项目、解释热度、查看仓库和 Release，管理关注 |
| 内容详情 | 阅读摘要与来源证据、相关事件、个人备注，收藏/稍后读/修正 |
| 我的整理 | 收藏、稍后读、已归档、需核对、回收站；按个人标签检索 |
| 全局搜索 | 检索标题、摘要、模型/仓库名称、标签与本人备注；默认排除回收站 |
| 来源管理 | 添加预设来源、启停、显示覆盖范围和同步状态、受限重试 |

首页以内容列表为主，最多显示简短的新增数量和来源状态，不先放大屏统计图。第一屏应能看到真实资讯、筛选和来源健康情况。

关注是跟踪模型/项目实体；收藏是保存某一条资讯；稍后读是阅读意图；已读是阅读状态；归档是个人列表可见性。这些状态独立，不能用一个状态字段互相覆盖。打开详情或原文后标为已读，并可手动恢复未读；仅滚动经过不算已读。

## 10. 电脑端与手机端

同一个响应式网站，两端共享账号与内容。电脑采用侧栏、搜索和较完整的列表信息；手机采用四个底部主入口“动态 / 模型 / 项目 / 我的”，筛选收进面板，详情独立阅读。具体页面行为见 [双端体验规格](v1-responsive-experience.md)。

- 手机保留标题、变化/用途、来源、时间和收藏入口；版本适用范围、更多来源和热度窗口在详情可达，不靠悬停。
- 手机也能修正资料、管理来源、查看同步失败和导出数据；批量操作使用显式选择模式，不能只有桌面功能入口。
- 个人整理状态同步到服务端。滚动位置、临时筛选和未保存输入以当前设备/会话为主，不强行覆盖另一设备正在使用的页面。
- 保存成功才展示成功反馈；网络失败保留输入，不能以本地临时效果冒充已跨端保存。两设备同时修改时提示冲突或版本差异，避免静默覆盖。
- 首版在线使用，不承诺离线阅读、安装到桌面或系统推送。

## 11. 概念数据模型与系统职责

这是逻辑设计，不是数据库表结构或接口代码。

| 概念 | 保存什么 | 关键关系 |
| --- | --- | --- |
| 来源与订阅 | 官方地址、类型、启用状态、周期、采集边界、健康状态 | 一个来源产生多条来源记录 |
| 来源记录 | 稳定外部标识、URL、标题、有限摘要、来源时间、版本/内容指纹 | 多条来源记录可指向同一事件 |
| 资讯事件 | 类型、统一展示字段、可信度/核对状态、修订历史 | 关联模型/项目实体和全部依据 |
| 模型/项目实体 | 稳定标识、别名、厂商或仓库、主题、原站链接 | 同一实体有多个独立事件 |
| 项目观测 | 仓库标识、快照时间、Star 等可核验值 | 多次观测产生带窗口的增长信号 |
| 个人整理 | 已读、收藏、稍后读、归档、标签、备注、人工覆盖 | 附着于事件或关注实体，不改写来源事实 |
| 同步记录 | 运行起止、覆盖区间、新增/更新/去重数、失败与重试 | 解释内容时效、部分成功和历史缺口 |

职责分为来源获取、标准化与归并、持久化与个人整理、站内检索展示、任务状态与运维。先按这些职责组织一个可维护系统，不预设微服务。后续技术 ADR 必须说明定时任务在网站无人访问时如何运行、如何避免重复任务、如何恢复中断和备份全部关系。

## 12. 首版验收与后续设计

- 至少验证两个不同官方公告来源及 GitHub 项目发现/Release 路径，定时任务在浏览器关闭时仍可工作；不是仅点击页面才拉取。
- 同一来源重复运行、新旧公告修订、跨源同事件、模型新版本、人工修改后重同步均有验收案例。
- GitHub 初次观测不显示虚构增长；已有两次快照后，显示可核算的净差、起止时间和采样范围。
- 来源故障、限流、部分成功、无新增、时间缺失和长时间无更新在界面上可区分。
- 手机和电脑均完成登录 → 浏览 → 筛选/搜索 → 详情/原文 → 收藏/备注 → 回找；手机可处理需核对和来源重试。
- 导出包含内容、来源、实体、标签、收藏/关注/阅读状态、个人备注和必要修订说明，能说明字段含义；恢复按既有备份门禁验证。
- 使用合成数据验证 10,000 条资讯的查询预算，并执行既有 UI、权限和上线门禁；当前文档通过检查不代表这些项目已验收。

设计推进顺序：先收敛首批来源与上述范围 → 设计首页、详情、模型页、项目页的电脑/手机视觉稿 → 确定采集、存储、登录和部署 ADR → 再进入实现。视觉稿阶段继续遵循 Ant Design 和现有设计令牌。
