# 项目章程

状态：首版 AI 资讯产品实现与验证。日期：2026-11-04。产品负责人：Hulinger。

## 目标与原则

这是自己长期使用的 AI 资讯集合工具，部署后可在受保护的网络入口访问。首版把模型更新、GitHub 有趣开源项目等信息自动收集、整理到自己的站点，并能在电脑和手机上阅读、查找、修正和带走自己的数据。私有性、可靠性、易用性和可维护性优先于功能数量。

用户已确认：使用 Git 管理版本与分支；UI 采用 Ant Design；按上线项目建设并提前明确规范；首版自动收集并汇总 AI 资讯，支持人工修正；电脑和手机适配。产品设计通过后，用户进一步授权开发可部署网站并创建独立 GitHub 仓库，README 提供完整介绍与 Docker 安装流程；目标为用户自己的服务器。用户随后明确要求仓库命名为 `hulinger-Information-Gathering-Station` 并公开代码，变更依据见 [ADR 0004](adr/0004-public-source-repository.md)。

## 初始业务范围

以下按用户明确的 AI 资讯方向收敛。详细流程、概念数据关系及可调整默认值见 [首版产品设计](design/v1-product-design.md)，范围变化记录于 [ADR 0002](adr/0002-ai-information-v1.md)。

| 范围 | 首版验收方向 |
| --- | --- |
| 信息收集 | 从公开白名单来源定时收集模型/产品公告、AI 项目及相关工具动态；手动补充链接；同步状态与覆盖边界可见 |
| 自动汇总 | 校验、去重、分类、关联实体及来源摘要；有效条目自动入站，异常进入需核对；保留来源和时间依据 |
| 信息整理 | 编辑、标签、收藏、稍后读、备注、归档和恢复；人工修正不被再次采集覆盖 |
| 信息查找 | 搜索标题、摘要、实体和备注，按类型/来源/标签/时间/状态筛选；无结果有清除条件入口 |
| 信息使用 | 查看模型/项目时间线、关注对象、打开原文；项目热度可解释，未知或过期数据不伪装为实时事实 |
| 双端体验 | 同一响应式网站覆盖电脑和手机；个人状态跨端一致，核心操作两端都能完成 |
| 数据自主 | 可导出完整个人数据，格式有版本说明；如启用导入，须有重复处理规则和失败报告；备份恢复另按上线门禁执行 |
| 私有访问 | 只允许本人登录后访问内容、搜索、导出及附件；禁止匿名注册 |

首版包含经过验证的 RSS/Atom、官方 API 及逐源适配的公开网页采集，必须通过既有安全门禁；不开放任意网站爬取。AI 中文摘要/翻译是可关闭的增强，不作为自动汇总的必要条件。公共分享、多用户协作、付费系统、浏览器插件、原生 App 和通知推送不纳入当前范围。用户追加的 0.2.0 私有大文件云盘依 [ADR 0005](adr/0005-large-file-drive.md) 纳入：保持单人登录/MFA 边界，支持上传、续传、下载和文件生命周期，补齐文件存储、配对备份及保留服务器定制的更新流程。

## 信息与数据约定

### 0.4.0 格式转换

依据 [ADR 0007](adr/0007-private-format-conversion.md)，小工具新增统一中文转换工作台，使用 ConvertX、Transmute、Stirling-PDF 核心及 ncmdump-net。用户确认服务器采用 Docker / WSL2 运行引擎，文件保留 24 小时。源文件、后台任务与输出按账号隔离；切换支持同一目标的引擎复用上传，不开放匿名转换、远程 URL 抓取或账号间分享。结果作为临时数据，不替代云盘与备份。

### 0.3.0 授权范围扩展

依据 [ADR 0006](adr/0006-managed-accounts-and-tools.md)，用户明确要求 admin 管理成员，并选择“所有功能，但每个账号的数据独立”。私有边界扩展为受邀请的账号，仍关闭公开注册、匿名访问与账号间共享。账号管理与登录记录只对原主账号开放；成员可使用独立的资讯、来源、整理、云盘、导出和小工具。新成员不复制已有资料，旧资料归原主账号。首个小工具为指定的破碎的像素地牢 Web 版，游戏存档按账号同步，保留对应源码供后续开发。

主账号继续要求 MFA，成员仅用用户名和密码登录；停用、改密和撤销会话立即影响后续请求。保留期清理覆盖停用成员，停用不允许新采集或生成导出。多账号结构启用后，回退须使用升级前配对快照，不能直接启动单账号旧版应用。

- 明确信息的稳定标识、内容类型、标题、来源、创建/更新时间及状态；可选字段可为空，不用占位假值冒充真实内容。
- 来源发布时间、本站发现/同步时间分开；来源只有日期时不补造时分。事实、来源摘要、人工修正和可选 AI 生成内容分别标记。
- 模型/项目是持续跟踪的实体，版本变化是独立事件；跨源归并保留全部依据。GitHub 增长来自真实观测窗口，不能用累计 Star 冒充近期增长。
- 业务时间统一存储为带时区语义的 UTC 时间；界面默认按 Asia/Shanghai 展示，可在后续需求中扩展。
- 保存、编辑、删除、导入需要有明确成功/失败结果。重复点击不得制造重复写入。
- 删除先进入可恢复状态，默认保留 30 天；永久删除须明确告知范围并二次确认。过期清理需要独立任务与运行记录，不能仅依赖页面隐藏；按首版设计保留最少去重标识，避免已删除条目被自动再次收集。
- 导出须包含信息、关联分类/标签和必要元数据；有附件时须定义附件导出方式。导出不是数据库备份的替代品。
- 生产数据不用于演示、截图、自动化测试或错误日志。测试使用合成数据。

## 阶段与验收

| 阶段 | 交付要求 |
| --- | --- |
| 0：规范基线 | 规范可读、Git 边界正确、基础检查可运行；不等同于产品可用 |
| 1：可实现方案 | 产品与双端页面设计、来源策略明确，数据模型、定时采集、应用技术栈、身份验证与部署 ADR 完成 |
| 2：可用闭环 | 登录、自动采集、去重汇总、人工整理、搜索、归档/恢复、导出在持久化数据上通过验证 |
| 3：预发布 | 双端 UI、来源失败/限流、权限、迁移、备份恢复与目标设备验证通过 |
| 4：生产发布 | 上线门禁全部通过，有版本标签、发布记录和回滚材料 |

## 范围与规范变更

小的实现细节在 PR 说明；改变业务范围、设计体系、数据存储、身份验证、部署或安全边界时，先写 ADR（背景、备选方案、决定、影响、验收和日期）。硬约束变更需要产品负责人确认。每个需求说明谁在什么场景完成什么操作，以及成功、失败和空状态；不以「做得像大厂」代替验收条件。
