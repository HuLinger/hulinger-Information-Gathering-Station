# Windows 原生部署：保留本地定制的候选升级

适用：通过 Windows 服务运行 Node.js、PostgreSQL、采集 worker 和维护任务，前方已有 Caddy 或 Cloudflare Tunnel 的部署。继续使用现有服务账号、目录 ACL、身份配置、数据库、备份与监控；无需改成 Docker。Linux Compose 部署使用 [部署说明](deployment.md)。

更新工具先在**新目录**生成包含上游更新和本地提交的候选版本，安装依赖并运行检查、构建。生产源码、配置和服务保持原样。目标服务器上的定制补丁与服务管理脚本未包含在本仓库，因此工具只完成候选准备；实际合并结果、隔离恢复、迁移和服务切换须在服务器验证，不能把本地测试视为服务器已升级。

## 1. 首次取得工具并准备候选

旧版本可能尚无更新脚本。先把 [update-windows.ps1](../scripts/update-windows.ps1) 保存到生产源码目录以外的工具目录，再执行它。以下命令只下载本仓库脚本，所有路径由操作者填写：

```powershell
$toolDirectory = Join-Path $env:TEMP ('hulinger-update-tool-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $toolDirectory | Out-Null
$updater = Join-Path $toolDirectory 'update-windows.ps1'
Invoke-WebRequest -UseBasicParsing `
  -Uri 'https://raw.githubusercontent.com/HuLinger/hulinger-Information-Gathering-Station/main/scripts/update-windows.ps1' `
  -OutFile $updater

$source = Read-Host '当前生产源码的仓库根目录（绝对路径）'
$candidate = Read-Host '候选版本目录（绝对路径、尚不存在、父目录已建立）'
pwsh -NoProfile -File $updater -DeploymentSourcePath $source -CandidatePath $candidate
```

已安装 PowerShell 7 时使用 `pwsh`；仅有 Windows PowerShell 5.1 时可把最后一行换成 `powershell -NoProfile -File ...`，参数相同。脚本为 UTF-8，兼容中文和含空格路径。不改变系统执行策略；按现有主机的脚本签名与执行要求保存、审查并运行下载文件。

要求 Git、Node.js 22 或更新版本和 `npm.cmd` 已在当前会话 PATH 中。0.3.0 的游戏构建还要求 JDK 17+（`JAVA_HOME` 或 PATH）及 `tar.exe`，首次构建需要访问 Gradle 与 Maven Central。Java 仅用于候选构建，不新增运行服务。脚本不会升级 Node.js 或 PostgreSQL，也不会改变现有服务的内存上限。默认拉取上游 `main`；如已有经审查的发布提交或标签，使用 `-UpstreamRef <完整提交号或标签>`。报告会记录实际拉取的完整提交号，切换时使用同一个已验证候选目录。

源目录必须是该项目的独立仓库根，已提交的本地定制会完整保留。若有未提交或未跟踪的源码，工具会停止，请先把需要保留的代码提交到本地分支；真实 `.env`、备份、状态目录和密钥继续留在 Git 外。工具不读取部署补丁文件来猜测覆盖顺序，不执行 `reset`、`clean`、`stash` 或强制覆盖。

候选目录必须与源目录独立、互不嵌套，不能经过目录联接或符号链接，也不能是已有目录。使用有权读取源仓库、写入候选父目录的运维账号；无需用生产 Web 服务账号执行安装。准备期间不要并行改动生产源码或运行另一个发布过程。

## 2. 工具做什么、如何判断结果

工具会依次执行：

1. 用不共享 Git 对象文件的克隆取得生产 HEAD，包括尚未进入上游的本地提交；不复制忽略的 `.env` 和运行数据。
2. 在候选的 `codex/chore/windows-candidate-*` 分支拉取指定上游并执行普通 merge。两条历史都必须是最终候选提交的祖先；没有冲突时，本地登录兼容、测试和运维文档等提交继续存在。
3. 运行 `npm ci`、`npm run setup`、`npm run check`、`npm run build`。任一步失败立即停止，保留候选与日志。
4. 核对生产 HEAD 和工作区仍未变化，输出版本号、Node 版本、提交号、保留的本地提交及检查结果。候选远程的推送地址被禁用，避免把部署定制意外推回公开仓库。

成功返回退出码 `0`，报告的 `status` 为 `prepared`，`productionActivated` 始终为 `false`。三个输出位于候选目录：

| 文件 | 用途 |
| --- | --- |
| `.deploy/windows-update/report.json` | 机器可读的来源、版本、完整提交号、每项检查退出码及准备状态 |
| `.deploy/windows-update/commands.log` | 合并和验证诊断；留在服务器本地，不提交 Git |
| `.deploy/windows-update/NEXT-STEPS.md` | 后续切换检查单，并指向本文 |

工具会临时移除当前进程继承的数据库连接、身份密钥、采集令牌、云盘路径和数据库测试开关，再运行候选命令；结束时恢复当前进程环境，不更改用户或系统环境变量。**准备阶段没有启用数据库集成测试，测试输出中的 skip 不算通过。** 数据库和迁移验证按下一节另行完成。

退出码非 `0` 表示未完成准备。冲突只留在候选中，生产继续使用旧版本。可执行以下只读命令查看冲突：

```powershell
git -C $candidate status
git -C $candidate diff --name-only --diff-filter=U
```

审查冲突时同时保留上游功能和已有登录定制的意图，不要对认证文件整份选择一边。使用熟悉的 Git 流程在候选解决并提交 merge，再把这个候选作为 `-DeploymentSourcePath`、另一个全新目录作为 `-CandidatePath` 重跑工具，以获得重新核验的报告。失败的候选可留作排查，工具不会自动删除它。

## 0.3.0 账号与游戏迁移

新增迁移 `005`、`006`、`007`：保留原主账号 ID、密码、MFA 和现有资料，将原资料归原主账号；移除仅单账号限制，并建立按账号隔离的业务表与游戏存档。找不到原主账号但已有资料时迁移会停止，必须先核实来源，不能猜测归属或清空数据。

升级前完成配对备份，并停止旧 Web/worker 写入后运行迁移，重新授予运行角色权限。不要在多账号结构上同时运行旧 worker 或旧 Web。旧队列任务缺少账号信息时不会被随意分配，账号内已启用的来源由新 worker 重新按计划调度；检查来源状态与心跳。

切换时一起携带候选的 `.games/shattered-pixel-dungeon-web`、`.next`、`public` 与运行源码，不能只复制 `.next`。`npm run build` 已先执行 `build:game`，不缺游戏构建时才算完整产物。新增成员与游戏存档在数据库备份内；云盘仍需文件配对备份。保留私有存储路径与原身份密钥，不把浏览器临时存档当服务器备份。

验收主账号 admin 登录/MFA、成员创建/密码登录、停用/改密/撤销、登录记录、至少两账号资讯/来源/云盘/导出/存档隔离，并实际进行游戏保存与刷新恢复。账户迁移后的**回退不兼容只改应用路径**：须先关闭入口和停止写入，保护升级后的新增数据，恢复已验证的迁移前数据库/云盘/身份配置配对快照及旧产物，再核对恢复点后的数据影响。

## 3. 切换前在服务器完成的验证

先审查候选与原生产提交之间的差异，确认既有管理员登录名映射、仅限初始化的例外、相应测试及 Windows 服务文档仍符合预期。更新已有账号不需要重新执行 owner 初始化，也不应重置密码或生成新身份密钥。

使用现有**隔离恢复环境**和合成数据验证新迁移、运行账号授权、登录/MFA、退出后会话失效和采集。数据库连接必须指向明确命名的隔离测试库，云盘路径也必须独立；不要给测试进程生产连接串。仓库提供 [云盘集成测试](../tests/drive.integration.test.ts)、[身份集成测试](../tests/auth.integration.test.ts) 和 [存储恢复校验](../scripts/verify-drive-storage.ts)。集成测试使用显式测试连接创建独立临时数据库，需要隔离环境的建库权限；恢复校验只应对暂停写入的隔离恢复副本执行。

新云盘要求下列配置与运维一起落地：

| 项目 | Windows 部署要求 |
| --- | --- |
| 存储位置 | Web 和采集 worker 配置同一个绝对 `DRIVE_STORAGE_PATH`，位于源码和候选目录之外；使用真实目录，不使用 junction。应用在其下建立 `objects`。 |
| 文件权限 | Web、worker 服务账号可读写云盘目录，Caddy 快速下载账号只读，维护/备份账号可读取完整云盘树。候选由运维账号克隆，不继承旧源码目录的 ACL：另行验证 Web/worker 可读取候选源码、依赖和构建，Web 可写其运行缓存目录。沿用原服务隔离，不把目录授予 Everyone。 |
| 容量 | 检查磁盘余量、单文件上限、云盘配额和保留空间；配置含义见 [环境样例](../.env.example)。默认分片 16 MiB、上传 4 路，服务端并发上限 8。 |
| Caddy | 将仓库 [Caddyfile](../Caddyfile) 的云盘路由合入现有配置，保留原域名、Tunnel、TLS 和客户端地址策略；全部 `web:3000` 改为现有 Web 回环地址，文件根改为实际 `objects` 的 Windows 路径（含空格时加引号）。模板各处 `header_up X-Forwarded-For {remote_host}` 面向直接入口，Tunnel 部署须逐处沿用现有可信代理取址策略，否则会把所有访问者记录为 cloudflared 的回环地址。只信任已配置的代理链，不无条件信任客户端自带的 CF/X-Forwarded 头。使用 2.11.7 或经验证的更新安全版本，最低不能低于 2.11.2。 |
| 上传与下载 | 精确分片 PUT 路径允许 33 MiB；游戏存档 PUT `/api/tools/shattered-pixel-dungeon/save` 单独允许 32 MiB，其他业务接口继续保持小请求限制。下载必须先清除客户端 `X-Drive-*`，再验证登录/MFA、完成状态和安全文件名；不得单独暴露文件目录。保留 attachment、private/no-store、Range/If-Range，下载不压缩。 |
| 配对备份 | 维护服务须把数据库、云盘对象目录与恢复所需身份配置放进同一个加密备份点。备份期间暂停 Web 和 worker 写入及清理；现有只备份数据库的任务不自动覆盖新文件。保持既有每日/每周保留和独立故障域。 |
| 监控 | 现有健康、备份新鲜度和容量告警继续运行，并检查云盘磁盘和 worker 清理状态。测试一次上传、恢复和备份失败时的可见结果。 |

验证 Caddy 配置后，沿用当前的配置激活方式。仓库示例关闭 admin API，直接执行 `caddy reload` 会失败；这种配置应通过现有 Windows 服务管理脚本受控重启，不为更新临时开放管理端口。若仍使用其他代理，Node 的鉴权流式下载路径可用，但代理也必须允许分片上传和 Range 请求。

使用一份合成文件验证上传、暂停、换页/重启后重新选择原文件续传、下载字节一致、改名、回收站恢复及明确确认后的清理；再验证退出登录和未登录不能下载。浏览器并行保存能力取决于文件保存接口支持，手机或不支持的浏览器使用普通下载。实际传输速度需在服务器出口、磁盘、代理和客户端线路上测量。

最后从同一加密备份点恢复数据库与文件至隔离环境，停止该副本的写入，执行 `scripts/verify-drive-storage.ts` 核对文件大小和已记录分片 SHA-256；核对完成后才启动副本做登录与下载验证。不要让恢复副本的服务配置或存储路径指向生产目录。

## 4. 用现有服务管理脚本完成切换

仓库无法推断现有四个 Windows 服务的名称、服务包装器或维护脚本参数，因此不生成可能启动错误服务的自动激活命令。将候选的完整路径交给当前已经使用的服务管理流程，按以下顺序执行并保存结果：

1. 记录旧 Web/worker/维护任务的源码路径、工作目录、实际启动参数、服务账号和当前构建；核对候选报告为 `prepared`，确认候选已通过上述隔离验证。记录可恢复的加密备份点及匹配的旧提交。
2. 进入维护窗口，用已有管理脚本暂停 Web、worker 和可能写库或清理文件的维护任务，完成最后一个数据库与云盘的配对备份。PostgreSQL 服务通常继续运行，以便备份和迁移。
3. 通过现有受限配置加载方式，为候选执行 `npm run migrate`，使用已有迁移账号；检查退出码。不要在命令历史里写入密码，不要复制 `.env.example` 覆盖真实配置。迁移失败时保持应用停止并检查诊断。
4. 用实际服务身份先验证候选代码/依赖/构建可读、运行缓存可写，以及 Web/worker 的云盘写入、Caddy 和维护账号的文件读取。用现有服务管理脚本把 Web 和 worker 的工作目录/启动路径切到已验证候选，继续用原来的绝对路径或服务环境加载外置身份、数据库和存储配置，保留服务账号与原有内存限制；不能假定新工作目录存在 `.env`。维护任务应用已验证的云盘备份逻辑。按现有启动顺序启动并检查就绪；最后激活经过验证的 Caddy 配置。
5. 在真实 HTTPS 入口验证拥有者登录/MFA、原资讯和人工整理、采集、一次合成文件上传/续传/下载与清理；确认未登录请求被拒绝，检查健康、磁盘、备份和告警。记录实际服务路径和候选完整提交号，保留旧源码及构建。

不要仅因为工具退出成功就对外宣称生产已升级。上述步骤需要实际运行结果；服务器上的定制合并、服务切换、ACL、Cloudflare Tunnel、备份与速度均由目标环境验证。

## 5. 失败与回滚

候选准备失败不需要生产回滚，因为工具未切换服务。解决构建或冲突问题后重新准备候选，不用覆盖旧生产目录。

切换后的故障先暂停写入并保存诊断。在数据库仍与旧版兼容时，使用原服务管理脚本恢复已记录的旧工作目录和启动参数；保留新云盘目录与元数据，不因旧版没有云盘页面而删除文件。迁移兼容性应已在隔离环境验证，不能仅依据 Git 回退推断成立。

如果需要恢复数据库，应从同一备份点同时恢复数据库、云盘和身份配置，先说明备份点之后写入的影响，再按既有隔离恢复流程执行。不要清空生产库、重新初始化管理员或只恢复数据库而丢下不匹配的文件目录。

工具回归命令：`pwsh -NoProfile -File tests/update-windows.test.ps1`。该测试使用临时的真实 Git 仓库验证两条本地提交保留、冲突、原目录不变、校验失败和路径边界；npm 子进程使用确定性夹具，不能代替候选自己的 `npm ci/check/build` 或实际服务切换验证。Git 独立克隆行为依据 [git-clone 文档](https://git-scm.com/docs/git-clone)，进程级环境隔离依据 [PowerShell 环境变量文档](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables)。
